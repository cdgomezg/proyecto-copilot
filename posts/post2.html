Estilos Arquitectónicos más utilizados

Qué es (minimal)

Los estilos arquitectónicos son guías para organizar componentes y comunicación. Elegir uno afecta mantenimiento, escala y velocidad de entrega.

Resumen rápido de estilos

Los 5 Estilos Clave: Comparativa Detallada

Monolito ⭐ ⭐⭐ MVPs, startups pequeñas Bajo inicial, alto después

1. Estilo Monolítico

Qué es: Todo el código (UI, lógica, datos) en un solo proceso. MonoApp incluye API endpoints, business logic, database connection y UI templates en una única aplicación.

Ventajas: Fácil de desarrollar, deployar, debuggear. Ideal para MVP.

Desventajas: Todo crece junto. Si escalas recomendaciones, escalas TODO.

Empresas que lo usan: Dropbox (al inicio), Instagram (primeros años).

2. Estilo en Capas (N-Capas)

Qué es: Separación horizontal: Presentation → Business → Data.

Capas: Presentation Layer (Controllers, Views) → Business Layer (Services, Validators) → Data Layer (Repositories, Queries).

Ventajas: Responsabilidades claras, fácil mantener, teams pueden trabajar en paralelo.

Desventajas: Acoplamiento horizontal (cambios propagan capas abajo).

Casos reales: WordPress (con plugins), e-commerce tradicionales.

3. Estilo MVC (Model-View-Controller)

Qué es: Separación de concerns: datos (Model), presentación (View), lógica (Controller). User Input → Controller → Model (process) → View (render HTML).

Frameworks: Rails, Django, ASP.NET MVC, Laravel.

Ventajas: Muy usado, entendible, UI desacoplada de lógica.

Desventajas: Controllers pueden crecer mucho (fat controllers).

4. Estilo Cliente-Servidor

Qué es: Cliente (UI/lógica) y Servidor (datos/reglas) comunicándose vía API. Browser/Mobile App ↔ REST API ↔ Backend (Java/Node) ↔ DB.

Empresas: Gmail (SPA), Facebook, Airbnb (todo basado en APIs).

Ventajas: Frontend y backend desacoplados, múltiples clientes (web, app).

Desventajas: Más tráfico de red, lógica duplicada posible.

5. Estilo Microservicios

Qué es: Múltiples servicios pequeños, independientes, comunicándose vía eventos/APIs. API Gateway con User Service, Order Service, Payment Service, Notification Service y event bus (Kafka).

Empresas: Netflix, Uber, Amazon, Spotify (todos usan).

Ventajas: Equipos autónomos, escala independiente, deploy frecuente.

Desventajas: Complejidad operativa (containerización, orquestación, observabilidad).

Casos de Uso Reales

  • Facebook: Monolito → Capas → MVC. Escala con caché (Memcached) y sharding de DB.
  • Amazon: Monolito inicial, luego Microservicios (mandato interno 2002). Cada equipo dueño de su servicio.
  • Uber: MVC al inicio, migró a Microservicios cuando se escaló a 40+ países.
  • Twitter: Rails (MVC) al inicio, luego polyglot con Scala, Java, Go para diferentes servicios.

Cómo Elegir el Estilo Correcto

Preguntas a hacerse:

  • ¿Cuántos usuarios esperados en 1 año? (1K → Monolito, 1M+ → Microservicios)
  • ¿Cuántos equipos? (1-2 → Monolito, 10+ → Microservicios)
  • ¿QPS esperado? (10 → Monolito simple, 10K → necesitas escalar)
  • ¿Latencia crítica? (si sí, considera CQRS)
  • ¿Presupuesto ops? (Microservicios es caro en DevOps)

Regla general: Empieza simple (Monolito/Capas), migra cuando duela.

Anti-patrón: Microservicios Prematuros

El error más común: "Netflix usa Microservicios, entonces yo también." Microservicios tienen overhead: latencia de red, dificultad de debugging, dificultad de testing distribuido.

Netflix empezó como Monolito y migró a Microservicios cuando realmente lo necesitó (años después, con cientos de ingenieros).

Recursos y Referencias

  • Libro: "Building Microservices" (Newman) — guía de migración.
  • Artículo: Martin Fowler - Microservices — definición estándar.
  • Doc: 12 Factor App — best practices para servicios escalables.
  • Herramientas: Docker, Kubernetes, Istio (para orquestar microservicios).
